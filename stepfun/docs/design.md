# 设计说明

## 目标分解

赛题要求把「端侧 embedding」和「库内混合检索」串成一条可演示的链路。拆成三个职责边界：

1. **浏览器**：加载 ONNX 权重、把文本编码成向量。模型选择、精度、设备都在浏览器侧决定，
   原文不离开页面（只发送向量 + 需要的元数据）。
2. **Node 桥**：把 HTTP 请求翻译成 seekdb SDK 调用。它**不做**任何候选合并、打分或重排，
   否则「检索由 seekdb 完成」就不成立。
3. **seekdb**：保存向量与文本，负责全文索引、HNSW 索引以及两路候选的融合。

## 为什么是一条语句

`seekdb@1.4.0` 的 `Collection.hybridSearch()` 会构造 `DBMS_HYBRID_SEARCH` 的 `search_parm`，
由数据库返回并执行检索 SQL：全文分支 `MATCH (...) AGAINST (...)` 命中全文索引，向量分支
`l2_distance(embedding, :query)` 走 HNSW，最后 `RRF` 在库内融合。桥接层只拿到最终结果行，
所以「一次候选检索 = 一条 seekdb 语句」。

如果把关键词候选和向量候选分别查出来再在 Node 里合并，就会退化成两条语句、且融合发生在客户端，
这正是赛题禁止的形态。

## RRF 参数

`rankWindowSize = 60`、`rankConstant = 60`：窗口覆盖两路各 60 条候选，常数取 RRF 经典值，
避免头部单条极端分数主导融合顺序。`query` 与 `knn` 的 `nResults` 都取用户 TopK，
保证每个分支都有足够候选进入融合。

## 降级策略

- **设备**：`navigator.gpu.requestAdapter()` 成功且返回 adapter 才用 WebGPU，否则 WASM；
  用户可以手动覆盖（便于在同一台机器上对比两条路径）。
- **模型源**：默认 `hf-mirror.com`，可改成任意 Hugging Face 兼容镜像，便于离线/内网演示。
- **权重传输**：镜像站不返回 CORS 头，浏览器直连会 `Failed to fetch`（已实测）。因此权重统一
  由 Node 桥代理：浏览器请求同源 `/api/model/<path>`，桥用 `fetch` 取上游并流式转发，
  并写入 `cache-control: public, max-age=86400`。副作用是内网部署时只需桥能出网，
  浏览器不必可访问外网。
- **权重精度**：`q8`（INT8 动态量化，默认）、`fp16`（WebGPU 下可用）、`fp32`（对照基线）。
  切换精度只需重新加载模型，向量维度不变（384），因此不必重建 collection。
- **后端不可用**：`/api/health` 失败时页面顶部状态条直接显示原因，不会静默失败。

## 安全与边界

- 查询文本在入参前做白名单式清洗：去引号、反斜杠、控制字符，截断 512 字符。原因是
  `whereDocument.$contains` 最终会拼进 `MATCH ... AGAINST`，不清洗存在注入风险。
- 向量维度在 collection 首次创建时固定；换模型（维度不同）需要「重建 collection」。
- 桥接层没有鉴权：演示默认绑定本机，若要对外暴露需要加认证与限流。

## 取舍

| 选择 | 理由 | 代价 |
| --- | --- | --- |
| React + Vite 单页 | 构建快、依赖少，评审 `npm install && npm run dev` 即可跑 | 没有路由/账号体系 |
| 桥接层用官方 `seekdb` SDK | 保证 `search_parm` 与库内函数签名一致，减少手写 SQL 的错误面 | SDK 版本需 >= 1.4.0 |
| 原文也存进库（`documents`） | 检索结果可直接展示原文，演示体验完整 | 库内保留文本，与「文本不出设备」仅指**不经过第三方**，桥接层仍可见 |
| INT8 作为默认精度 | 体积约为 FP32 的 1/4，加载与推理更快，语义检索质量损失可接受 | 极细粒度语义任务可能略逊于 FP32 |

## 后续可做

- 分块策略：当前按行切分，长文档应改为按标题/段落切块并保留 `parent_id`；
- 结果高亮：把命中的查询词在原文中做偏移高亮；
- 多 collection：按知识库分区，检索时按 `where` 过滤；
- 评测脚本：用固定问题集对比 INT8/FP32 的 Recall@k，输出质量-性能曲线。

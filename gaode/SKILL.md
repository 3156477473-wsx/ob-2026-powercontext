# 周边去哪儿 · 步行可达地点推荐

## 1. 这个 Skill 做什么

一句话需求进来，输出「最多 3 个从同一起点步行可达的地点」，每个地点带**名称、地址、步行距离、步行时间、一句有数据依据的推荐理由**。

- **适用**：单轮、单起点、单类型（咖啡馆 / 餐厅 / 公园 / 便利店 / 药店 …），可带步行时间上限、数量上限、排序偏好。
- **不适用**（遇到就直说，别硬编）：多站行程串线、跨城路线、实时排队/等位、实时营业状态核实、语音导航。
- **硬性红线**：
  1. 最多推荐 3 个；用户给的 K 更小就按 K。
  2. 步行距离与时间**必须来自步行路线规划工具**，不能用直线距离、地图估算或自算速度冒充。
  3. 地点名称、地址、坐标全部来自工具返回，**不得编造、不得补全记忆里的“大概位置”**。
  4. 超过用户时间上限的地点，**不得**出现在「符合条件的推荐」里。
  5. 排队、安静程度、是否营业、是否有座位等无数据支撑的信息，一律标 `未核实`。

## 2. 先把需求拆成一张表

在调用任何工具之前，先从用户话里抽出这些槽位（缺的记 `未指定`）：

| 槽位 | 说明 | 例 |
| --- | --- | --- |
| 城市 | 用于地理编码与关键词搜索 | 杭州 |
| 起点 | 地名或 `经度,纬度` | 西湖文化广场 / `120.155070,30.274084` |
| 地点类型/关键词 | 用户要找什么 | 咖啡馆 |
| 步行时间上限 | 分钟 | 15 |
| 数量上限 | ≤3 | 3 |
| 排序偏好 | 近 / 评分高 / 环境好 | 优先近一点 |
| 其他期望 | 往往无法核实 | 安静、不用排队、现在营业 |

**起点缺失时**：先 `maps_geo`（地名 → 坐标）；仍拿不到就用「城市 + 关键词」做 `maps_text_search`，并在回答开头写明假设（“起点按杭州市中心处理”）。单轮评测里不要停下来反问，先给可用结果再说明假设。

## 3. 执行流程（五步，按序做）

### 第 1 步 · 定位起点

- 用户给了坐标 → 直接用（高德格式是 **`经度,纬度`**，经度在前，别写反）。
- 用户给了地名 → `maps_geo(address=起点, city=城市)`，取返回的 `location`。
- 想确认起点落在哪个区 → `maps_regeocode(location=起点坐标)`（可选，仅用于把地址写清楚）。

### 第 2 步 · 召回候选地点

主用周边搜：

```
maps_around_search(
  location = 起点坐标,          # 必填，"经度,纬度"
  keywords = 地点类型,          # 如 咖啡馆 / 餐厅 / 公园
  radius    = 搜索半径(米)      # 建议见下
)
```

半径估算：`半径 ≈ 步行上限(分钟) × 75 米/分钟`，向上取到 500 米的整数倍，**再放宽约 40%**，避免把“刚好在边界上”的点漏掉（超时与否交给第 4 步的路线时间硬筛）。

- 15 分钟 → 约 1125 m → 取 `1500`
- 10 分钟 → 约 750 m → 取 `1000`
- 20 分钟 → 约 1500 m → 取 `2000`
- 用户没给时间上限 → 取 `2000`，并在回答里说明“按 2 公里周边范围搜索”。

**类型很模糊时**（“附近有什么值得去的”“随便逛逛”）：按 `景点`（或 `公园`）先搜一轮，开头写明“按『值得去的地方 = 景点』理解”；回答末尾补一句「想找吃的/喝的可以告诉我具体类型」。不要因为类型模糊就放弃查询。

**候选不足或为空时**（这是常见情况，别急着收工）：

1. 换同义词再搜一次（见下表）。
2. 用关键词搜补一轮：`maps_text_search(keywords=类型, city=城市)`。
3. 仍不足 → 如实说明，并给放宽建议（放大半径 / 换类型 / 放宽时间），**不要凑数**。

常用类型的同义写法（按需挑 1~2 个重搜即可，别把全部词都打一遍）：

| 用户说法 | 可换的关键词 |
| --- | --- |
| 咖啡馆 | 咖啡、咖啡厅、咖啡馆、星巴克 |
| 餐厅 / 吃饭 | 餐厅、美食、饭店、快餐、火锅 |
| 公园 / 散步 | 公园、绿地、广场、植物园 |
| 便利店 | 便利店、超市、罗森、全家 |
| 药店 | 药店、药房、大药房 |
| 健身房 | 健身房、游泳馆、瑜伽 |
| 洗手间 | 公共厕所、卫生间 |

### 第 3 步 · 去重与预筛（不调工具，纯筛选）

- 按 POI `id` 去重（同一家店常被多个关键词重复召回）。
- 剔除类型明显不符的（找咖啡馆却返回加油站、便利店）。
- 按到起点的距离字段/返回顺序排序，保留 **8~10 个**进入下一步。宁可多测几个，也别只测 3 个就下结论。

### 第 4 步 · 逐个规划步行路线

```
maps_direction_walking(
  origin      = 起点坐标,      # "经度,纬度"
  destination = 候选坐标       # "经度,纬度"
)
```

从返回的 `paths[0]` 里取 **距离（米）** 与 **耗时（秒→分钟）**。这就是最终要写进回答的数字，四舍五入到 10 米、1 分钟。

- 一次评测里对同一批候选**最多测 10 个**，够用就停。
- 需要交叉验证时可用 `maps_distance(origins=起点坐标, destination=候选坐标, type="3")`（`type`：`"0"` 直线、`"1"` 驾车、`"3"` 步行），但**对外只报步行路线规划的结果**。
- 想知道候选的完整地址/电话 → `maps_search_detail(id=候选 id)`。

### 第 5 步 · 硬筛 + 排序 + 取前 N

1. **硬筛**：`步行时间 ≤ 用户上限` 才算“符合条件”。超时的点一律不进推荐表（可在“未列入”里一句话带过，别混进正文表格）。
2. **排序**：
   - 用户说“优先近一点” → 按**步行时间升序**（时间相同再按距离）。
   - 用户没说 → 同样按步行时间升序，最稳、最不容易被判“排序与数据不一致”。
   - 用户明确要“评分高/环境好” → 先按该条件，再按步行时间；评分之外的软性描述只在有数据时使用。
3. **截断**：取前 `min(3, 用户要求的数量)` 个。

## 4. 工具速查（参数名要和这里一致）

| 用途 | 工具名 | 关键参数 | 备注 |
| --- | --- | --- | --- |
| 地址 → 坐标 | `maps_geo` | `address`、`city` | 返回 `location` = 经度,纬度 |
| 坐标 → 地址 | `maps_regeocode` | `location` | 拿行政区/街道 |
| 周边搜 | `maps_around_search` | `location`（必填）、`keywords`、`radius` | 本题主力 |
| 关键词搜 | `maps_text_search` | `keywords`（必填）、`city`、`types` | 周边搜不够时补 |
| POI 详情 | `maps_search_detail` | `id` | 拿完整地址 |
| 步行路线 | `maps_direction_walking` | `origin`、`destination` | **唯一可用于报时间的工具** |
| 距离测量 | `maps_distance` | `origins`、`destination`、`type` | `type="3"` 步行 |
| 驾车/骑行/公交 | `maps_direction_driving` / `maps_bicycling` / `maps_direction_transit_integrated` | `origin`、`destination`（公交另需 `city`、`cityd`） | 本题不用 |
| 天气 | `maps_weather` | `city` | 仅在用户提到天气时用 |

> 平台注入的工具名可能带服务器前缀（例如 `amap-maps__maps_around_search`）。**按名字后缀匹配调用**即可，参数名保持不变。坐标一律 `经度,纬度`，多位小数直接用返回值，不要自己改写。

## 5. 回答格式

先一句话给结论，再上表格，最后一段说明数据与限制。全程不用 JSON、不用代码块。

```
一句话结论：<起点> 步行 <N> 分钟内找到 <M> 家 <类型>，按距离从近到远推荐如下。

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
|---|------|------|----------|----------|----------|
| 1 | XX咖啡(XX店) | XX路XX号 | 约 420 米 | 约 6 分钟 | 最近的一家，出站直走即到 |
| 2 | ... | ... | ... | ... | ... |

说明：距离与时间为高德步行路线规划结果；营业状态、排队情况未核实。
```

写回答时的几条硬要求：

- 表格里**每一行的数字都必须来自该地点的路线规划结果**；没测出来的点不要进表。
- 推荐理由 **≤ 25 字**，且能从数据里找到依据（最近 / 类型匹配 / 在 XX 路沿线 / 沿路直走少拐弯）。不要写“环境安静”“很多人推荐”这类没有数据的话；真要提，就加 `（未核实）`。
- 距离用“约 XXX 米”（≥1000 米写“约 1.2 公里”），时间写“约 X 分钟”。
- 只列独立备选，不要把它们串成一条多站行程。

## 6. 异常与边界处理

| 情况 | 怎么答 |
| --- | --- |
| 结果不足 K 个 | 正常推荐已找到的，并说明“<N> 分钟步行范围内只找到 M 家符合条件的地点”，附放宽建议（扩大范围/换关键词） |
| 一个都没有 | 说明实际搜索半径与关键词，提出两个可执行建议（如“放宽到 20 分钟”“换成‘咖啡厅’再试”）；**不要列任何地点** |
| 路线查询失败/超时 | 该点标注“步行时间未取到（工具异常）”，**不计入符合条件**；若全部失败，直说服务异常并建议稍后重试 |
| 工具整体不可用 | 如实说明无法查询高德数据，不输出任何地点或数字 |
| 用户条件互相冲突（如“最近的 3 家但都要 5 分钟内”） | 先满足硬条件（时间），再说明数量无法满足 |
| 问营业/排队/安静 | 只给“未核实”，可建议用户打商家电话或看实时地图 |

## 7. 提交前自检（逐条打勾）

- [ ] 推荐数量 ≤ 3，且不超过用户要求
- [ ] 每个推荐都有：名称、地址、步行距离、步行时间、理由
- [ ] 所有距离/时间都来自 `maps_direction_walking`
- [ ] 表里没有超过用户时间上限的地点
- [ ] 排序方式与用户偏好一致（默认按时间升序）
- [ ] 起点坐标是 `经度,纬度`，没写反
- [ ] 没有编造的地点、地址、数字；软性信息标了 `未核实`
- [ ] 结果不足/失败时写了说明与放宽建议
- [ ] 没有输出任何 API Key、内部 ID 堆砌或原始 JSON

## 8. 示例（骨架，数字以工具实际返回为准）

**用户**：我在杭州西湖文化广场，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。

**执行**：

1. `maps_geo(address="西湖文化广场", city="杭州")` → 起点坐标
2. `maps_around_search(location=起点, keywords="咖啡馆", radius=1500)`
3. 去重后取前 10 个，逐个 `maps_direction_walking(origin=起点, destination=候选)`
4. 只保留耗时 ≤ 15 分钟的，按时间升序取前 3 个，必要时 `maps_search_detail` 补全地址

**回答**：

> 西湖文化广场步行 15 分钟内找到 3 家咖啡馆，按步行时间从近到远：
>
> | # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
> |---|------|------|----------|----------|----------|
> | 1 | （工具返回的店名） | （工具返回的地址） | 约 420 米 | 约 6 分钟 | 最近的一家，出广场直走即到 |
> | 2 | … | … | 约 700 米 | 约 10 分钟 | 类型匹配，沿主路直行好找 |
> | 3 | … | … | 约 980 米 | 约 13 分钟 | 备选，仍在 15 分钟内 |
>
> 说明：距离与时间为高德步行路线规划结果；营业状态与排队情况未核实。
